# База данных JetPing: Архитектура и Интеграция

## Как работает база данных
В проекте используется легковесная встроенная СУБД **SQLite3**. База данных представлена одним локальным файлом, путь к которому задается через переменные окружения (`JETPING_DATABASE_PATH`, по умолчанию `data/jetping.db`). 

Взаимодействие с базой данных реализовано через встроенную Python-библиотеку `sqlite3`. Поскольку Telegram-бот (на базе `python-telegram-bot`) работает асинхронно, а SQLite выполняет синхронные блокирующие I/O операции, запись в базу делегируется в отдельные системные потоки с помощью `asyncio.to_thread()`. Это гарантирует, что работа с диском не остановит обработку сообщений от других пользователей.

## Структура таблицы `searches`
Таблица `searches` предназначена для хранения истории поисковых запросов пользователей и минимальных цен, найденных по этим запросам.

| Поле | Тип | Описание и Назначение |
| :--- | :--- | :--- |
| `id` | `INTEGER` | Уникальный автоинкрементный идентификатор записи (Primary Key). Служит для однозначной идентификации каждой строки. |
| `user_id` | `INTEGER` | Telegram ID пользователя, который инициировал запрос. Позволяет связывать историю поисков с конкретными людьми. |
| `origin` | `TEXT` | IATA-код города вылета (например, `MOW`). Обязательный параметр для отслеживания маршрута. |
| `destination` | `TEXT` | IATA-код города прилета (например, `LED`). Второй компонент маршрута. |
| `departure_date` | `TEXT` | Дата вылета в формате ISO (`YYYY-MM-DD`). |
| `return_date` | `TEXT` | Дата возвращения в формате ISO, либо `NULL`, если пользователь искал билет в одну сторону. |
| `service` | `TEXT` | Название сервиса/провайдера (например, `Aviasales / Travelpayouts` или `Mock provider`). Нужно для понимания источника цены. |
| `price` | `INTEGER` | Найденная минимальная цена билета (в целых числах). Главная метрика приложения. |
| `currency` | `TEXT` | Буквенный код валюты (например, `rub`). Необходим для корректного отображения и сравнения цен. |
| `airline` | `TEXT` | Название или IATA-код авиакомпании. Поле опционально (`NULL`), так как не все провайдеры могут возвращать эту информацию. |
| `link` | `TEXT` | URL-ссылка на страницу бронирования билета. Опциональное поле. |
| `timestamp` | `TEXT` | Дата и время сохранения записи. Заполняется самой СУБД автоматически (`DEFAULT CURRENT_TIMESTAMP`). |

## Зачем нужны эти данные?
1. **Основа для будущих уведомлений ("Пингов"):** Наличие сохраненной истории цен по конкретным направлениям и датам — это фундамент для отслеживания падения цен. В будущем бот сможет сверять новые результаты с теми, что уже есть в БД, и уведомлять пользователя, если цена стала ниже.
2. **Аналитика:** База позволяет проанализировать, какие направления (`origin` -> `destination`) наиболее востребованы у пользователей бота.
3. **Логирование и отладка:** Сохранение точных данных, включая ссылки, помогает при отладке интеграций с внешними API (такими как Travelpayouts) и разборе возможных ошибок при получении цен.

## Как БД была внедрена в проект
Интеграция базы данных состоит из нескольких логических шагов:

1. **Настройки конфигурации (`config.py`):**
   * Класс `Settings` был расширен полем `database_path` типа `Path`. 
   * Значение по умолчанию загружается в `load_settings` с фоллбеком на `data/jetping.db`.

2. **Слой хранения данных (`db.py`):**
   * Реализована функция `init_db(db_path)` для автоматического создания директорий и таблицы `searches`, если они отсутствуют.
   * Создана функция `save_search`, формирующая и выполняющая SQL `INSERT` запрос. Она переносит данные из датаклассов `FlightSearch` и `PriceQuote` в плоскую структуру таблицы.

3. **Инициализация в боте (`bot.py`):**
   * В функции `create_application` путь к базе данных внедряется в контекст приложения бота (`application.bot_data["database_path"]`), что делает его доступным для всех обработчиков сообщений.

4. **Асинхронное сохранение данных (`bot.py`):**
   * На финальном этапе диалога (обработчик `return_date_received`), когда бот успешно получает цену от `PriceProvider`, вызывается функция сохранения.
   * Вызов обернут в `try/except` блок: если при записи на диск произойдет сбой (например, нет прав на запись в файл), это **не сломает** работу бота. В лог запишется ошибка, но пользователь все равно получит сообщение со найденной стоимостью билета.
